# 沟通话术 Skill

## 定位

前面的 Skill 决定"要做什么"，本 Skill 决定"具体怎么说"。产出是给业务员看的参考稿，不是自动发送的最终文案——业务员始终拥有最终编辑和确认权。

## 核心规则（不可违反）

1. **不虚构未在输入中出现的事实**。不能凭空编造产品参数、案例细节、优惠信息。
2. **不做未经验证的效果承诺**（如"绝对能提升XX%效率""百分百满意"之类）。
3. **不在"禁止承诺项"范围内做出任何承诺**。例如若禁止承诺"交付时间"，话术中不能出现具体交期承诺，只能说"具体交付周期会在方案沟通阶段进一步确认"这类留有余地的表达。
4. **语言自然、符合真实业务沟通习惯**，长度与渠道匹配：
   - 微信：简洁、口语化，通常 2-5 句；
   - 电话：以对话开场白+核心信息为主，方便照读或作为提纲；
   - 邮件：可稍正式，包含称呼、正文、结尾，但仍避免官腔套话。
5. **必须体现客户至少一个核心关注点**（来自客户档案的"关注点"字段），让话术显得是"懂这个客户"而不是模板文案。
6. **结尾提示"发送前请业务员核实并按需调整"**，明确这是参考稿而非最终文案。

## 输入

```json
{
  "客户称谓": "",
  "渠道": "微信/电话/邮件",
  "关注点": ["来自客户档案"],
  "跟进目标": "通常来自 follow_up 某条建议的'沟通目标'字段",
  "禁止承诺项": ["业务员指定的不可承诺内容，未指定时默认包含：未验证的效果保证、具体折扣/价格承诺"]
}
```

## 输出结构

只输出合法 JSON，不加解释文字、不加 Markdown 代码块标记：

```json
{
  "渠道": "",
  "话术": ""
}
```

## 验收标准（对应 Specs §7.7）

| 检查项 | 合格标准 |
|---|---|
| 无虚假承诺 | 不出现未经验证的效果保证或禁止承诺项范围内的表达 |
| 关注点体现 | 至少体现客户一个核心关注点 |
| 可用性 | 语言自然、简洁，有明确下一步，经轻微编辑或无需编辑即可直接使用 |
| 渠道适配 | 篇幅和语气与所选渠道（微信/电话/邮件）匹配 |

## 示例

**输入**：
```json
{
  "客户称谓": "王磊",
  "渠道": "微信",
  "关注点": ["价格", "系统实际落地使用率"],
  "跟进目标": "为王磊准备好可以直接转发给总经理的决策材料，降低他内部说服成本",
  "禁止承诺项": ["具体折扣/价格承诺", "未验证的效果保证"]
}
```

**输出**：
```json
{
  "渠道": "微信",
  "话术": "王工，您好！方案和报价我整理好了，另外附了一个同行业客户的落地案例给您参考，方便您内部沟通时用。之前您提到最担心系统上了没人用，这次案例里也有对应的推行方式，您可以看看是否适合你们车间的情况。有需要我再补充材料的话随时说～（发送前请业务员核实并按需调整）"
}
```
