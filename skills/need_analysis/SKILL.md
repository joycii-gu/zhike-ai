# 客户需求分析 Skill

## 定位

本 Skill 把"客户说了什么"升级为"客户真正需要什么、卡在哪"。这是知客 ZhiKe AI 区别于普通信息记录工具的关键一步：资深业务员能从零散对话中判断显性需求和潜在痛点，本 Skill 把这种判断能力拆解为可执行、可审查的规则。

## 核心规则（不可违反）

1. **显性需求必须能在原文证据中找到依据**，不得虚构。每一条显性需求最好能对应到 customer_profile 输出的"证据摘录"或原文片段。
2. **潜在痛点属于推断内容**，每一项必须以 `【推断】` 开头，不能写成确定结论。
3. **不得虚构客户预算、决策权限、采购时间点等敏感信息**；如证据不足，应写入"待确认问题"，而不是编造一个听起来合理的结论。
4. 待确认问题必须具有业务价值（能帮助业务员推进下一步），不能是无意义的套话。

## 输入

- 必需：`customer_profile` Skill 输出的客户档案 JSON。
- 建议：`customer_profile` 步骤1 输出的"证据摘录"数组，以及原始沟通文本（用于交叉核对，避免脱离原文过度发挥）。

## 输出结构

只输出合法 JSON，不加解释文字、不加 Markdown 代码块标记：

```json
{
  "显性需求": ["必须能在原文找到依据"],
  "潜在痛点": ["【推断】开头，每项都要标注"],
  "决策因素": ["客户最终决策会考虑的关键因素，如价格/效果/合规/内部推动成本等"],
  "成交阻碍": ["当前阻碍推进的具体因素"],
  "待确认问题": ["至少1条，需具有业务价值，业务员下次沟通可直接问"]
}
```

## 验收标准（对应 Specs §7.4）

| 检查项 | 合格标准 |
|---|---|
| 显性需求准确性 | 至少识别一项主要需求，且能对照原文验证 |
| 潜在痛点标注 | 所有潜在痛点均以【推断】开头，不与显性需求混淆 |
| 待确认问题 | 至少提出一项有业务价值的待确认问题 |
| 敏感信息审慎度 | 不虚构预算、决策权限或采购时点；证据不足时写入待确认问题而非编造结论 |

## 示例

**输入（customer_profile 输出的档案 + 证据摘录）**：
```json
{
  "基本信息": { "称谓": "王磊", "行业": "制造业", "角色": "信息化负责人（非最终决策人）" },
  "核心需求": ["生产管理系统替代Excel", "需对接现有ERP"],
  "关注点": ["价格", "系统实际落地使用率"],
  "决策阶段": "比较/评估阶段，需总经理最终拍板",
  "时间计划": "下月内部开会，若通过则Q3落地",
  "待确认事项": ["具体预算范围", "总经理的决策倾向", "现有ERP具体型号/接口情况"],
  "证据摘录": ["我们工厂想上一套生产管理系统，之前一直用Excel记，太乱了", "我不是最终拍板的，得我们总经理点头"]
}
```

**输出**：
```json
{
  "显性需求": ["用生产管理系统替代Excel记录方式", "需要与现有ERP系统对接"],
  "潜在痛点": [
    "【推断】此前上过系统但最终没人用，可能对新系统的可落地性和员工接受度存在顾虑",
    "【推断】作为非最终决策人，可能需要更有说服力的材料去说服总经理"
  ],
  "决策因素": ["总经理对价格和效果的最终判断", "系统是否能真正被车间和办公室员工用起来", "与现有ERP的对接可行性"],
  "成交阻碍": ["王磊不是最终拍板人，需要总经理认可", "此前失败经历可能带来内部推进阻力"],
  "待确认问题": [
    "总经理最关注的是价格、效果还是实施周期？",
    "上一套失败的系统具体卡在哪个环节（培训、易用性还是流程不匹配）？",
    "现有ERP的具体品牌/版本，便于确认对接方案"
  ]
}
```
