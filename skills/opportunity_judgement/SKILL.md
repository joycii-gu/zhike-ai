# 业务机会判断 Skill

## 定位

本 Skill 是知客 ZhiKe AI 最容易被滥用、也最需要克制的一环：新人业务员最常犯的错误是把"客户感兴趣"直接等同于"高意向客户"，导致资源错配、跟进动作过急。本 Skill 的核心不是给出一个乐观的分数，而是给出一个**有依据、可被质疑、正反信号都摆出来**的判断。

## 核心规则（不可违反）

1. **商机等级只能是以下五个值之一**："高"、"中高"、"中"、"低"、"暂不判断"。不允许自造其他等级或用百分比代替。
2. **不能仅因客户表达兴趣、礼貌性回应或提出问题就判定为"高"**。必须综合以下维度：
   - 需求匹配度（need_analysis 中的显性需求与产品的匹配程度）；
   - 预算明确度（是否有具体预算信号，还是仍是【未知】）；
   - 时间计划（是否有明确落地时间点）；
   - 决策权限（沟通对象是否是决策人，还是需要向上汇报）；
   - 风险因素（成交阻碍、竞品、内部推动阻力等）。
3. **必须同时列出"有利信号"与"风险因素/不确定事项"**，不能只列一边——即使商机等级判为"高"，也要列出风险；即使判为"低"，也要列出有利信号（如果有）。
4. 证据不足以支撑判断时，直接使用"暂不判断"，并说明还缺哪些信息，而不是勉强给出一个中间等级。

## 输入

- 必需：`need_analysis` Skill 输出的需求分析 JSON。
- 建议：`customer_profile` 中的预算信号、时间计划、当前阶段（用于交叉核对意向强度）。

## 输出结构

只输出合法 JSON，不加解释文字、不加 Markdown 代码块标记：

```json
{
  "商机等级": "高/中高/中/低/暂不判断",
  "判断依据": "简要说明为什么给出这个等级，引用具体信号",
  "有利信号": ["..."],
  "风险因素": ["..."],
  "不确定事项": ["..."]
}
```

## 验收标准（对应 Specs §7.5）

| 检查项 | 合格标准 |
|---|---|
| 判断有依据 | 商机等级与需求分析中的证据一致，"判断依据"能追溯到具体信号，而非泛泛而谈 |
| 审慎性 | 不因客户表达兴趣就直接判定高意向；缺乏关键信息（预算/决策权/时间）时不轻易给"高" |
| 双面呈现 | 有利信号和风险因素/不确定事项必须同时出现，不能只列一边 |
| 等级枚举合规 | 商机等级严格取自五个预设值之一 |

## 示例

**输入（need_analysis 输出 + 交叉信号）**：
```json
{
  "需求分析": {
    "显性需求": ["用生产管理系统替代Excel记录方式", "需要与现有ERP系统对接"],
    "潜在痛点": ["【推断】此前系统失败，对可落地性有顾虑", "【推断】作为非决策人需要说服总经理"],
    "决策因素": ["总经理对价格和效果的最终判断", "系统是否真正被用起来"],
    "成交阻碍": ["王磊非最终拍板人", "此前失败经历带来内部阻力"]
  },
  "预算信号": "【未知】未提及具体预算范围",
  "时间计划": "【事实】下月内部开会，若通过则Q3落地",
  "当前阶段": "【事实】比较/评估阶段"
}
```

**输出**：
```json
{
  "商机等级": "中",
  "判断依据": "客户有明确、具体的需求（替代Excel、对接ERP）且有初步时间计划（下月开会、Q3落地），属于正向信号；但预算仍未知、沟通对象非最终决策人、且存在历史失败经历带来的内部阻力，尚不足以判为中高或高",
  "有利信号": ["需求明确具体，非泛泛咨询", "有初步时间节点（下月开会、Q3目标）", "主动询问价格和对接方案，参与度较高"],
  "风险因素": ["预算范围完全未知", "王磊不是最终决策人，总经理态度未知", "此前系统落地失败，可能存在内部信任成本"],
  "不确定事项": ["总经理是否支持采购", "具体预算区间", "是否有竞品在同时对比"]
}
```
