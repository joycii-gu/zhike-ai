# 知客 ZhiKe AI：核心 Skills / Workflow

> 项目副标题：面向业务员的 AI 业务处理智能体  
> 适用阶段：S3 全球青年培育赛 · W2 复赛 · X创新赛道  
> 文档定位：W2 原型工作流设计与评测说明

## 1. 文档目的

本文件描述知客 ZhiKe AI 在 W2 阶段的核心 Skills、数据传递方式、事实边界和验收标准，用于说明项目如何从产品想法转化为可实现、可运行、可逐步验收的原型工作流。工作流是否已经完整运行，应以实际网页 Demo、运行记录和评测结果为准，不能仅由本文档替代证明。

知客不是依赖一个超长 Prompt 一次性生成所有内容，也不是围绕开放式聊天设计的普通聊天机器人。W2 原型采用链式 Skills 工作流，将客户信息解析、档案生成、需求分析、机会判断、跟进建议、话术生成和业务日报拆分为多个职责明确的处理环节。

每个 Skill 均定义以下内容：

- 明确的输入与输出；
- 单一、可解释的处理目标；
- 事实边界与关键规则；
- 可执行的合格标准；
- 可独立评测、调试和迭代的接口。

W2 仓库中的 `skills/*/SKILL.md` 是对应的可评审 Skill 定义，`src/skills.py` 提供本地 Mock 模式下的运行适配层，`src/agent.py` 通过 `MockProvider` 调用该适配层。这样，文档中的 Skill 边界与网页 Demo 的实际执行路径保持一致；真实模型或 HermesAgent 可在后续通过 Provider 接口替换，不改变公开报告结构。

## 2. 总体工作流

**客户信息输入 → Skill 1 客户信息解析 → Skill 2 客户档案生成 → Skill 3 客户需求分析 → Skill 4 业务机会判断 → Skill 5 跟进建议生成 → Skill 6 沟通话术生成 → Skill 7 业务日报生成**

工作流采用链式传递机制。前一个 Skill 的结构化输出经必要的字段校验后，作为后一个 Skill 的上下文输入。输出优先采用约定字段或 JSON Schema，避免不同步骤之间依赖自由文本猜测字段含义。

链式工作流遵循以下原则：

1. **结构化传递：** 客户字段、判断依据、待确认项和风险标记使用固定字段传递。
2. **证据可回溯：** 关键判断保留必要的原文证据片段。
3. **事实边界清晰：** 信息标注为“事实”“推断”或“未知/待确认”。
4. **上下文剪裁：** 后续 Skills 只读取当前任务需要的字段和证据，不重复读取全部原始聊天记录。
5. **逐级校验：** 每个 Skill 可单独检查输入、输出和错误来源，降低长链路调试成本。

这种设计可减少重复上下文造成的注意力衰减，降低信息误传和模型幻觉风险，并提高输出稳定性、可解释性与可评测性。

## 3. Skills 总览表

| Skill | 名称 | 输入 | 输出 | 主要价值 |
|---|---|---|---|---|
| Skill 1 | 客户信息解析 | 客户备注、聊天记录、电话或会议纪要 | 结构化客户字段与原文依据 | 从非结构化内容中识别有效业务信息 |
| Skill 2 | 客户档案生成 | Skill 1 解析结果 | 统一客户档案 | 降低人工整理成本，形成可核查客户视图 |
| Skill 3 | 客户需求分析 | 客户档案、关注点、证据片段 | 需求分析报告 | 区分显性需求、潜在痛点和待确认问题 |
| Skill 4 | 业务机会判断 | 需求分析、预算与时间信号、风险因素 | 机会等级、依据与不确定因素 | 审慎辅助客户优先级判断 |
| Skill 5 | 跟进建议生成 | 档案、需求分析、机会判断 | 可执行跟进计划 | 将分析结果转化为下一步行动 |
| Skill 6 | 沟通话术生成 | 客户关注点、渠道、跟进目标与约束 | 可编辑沟通话术 | 缩短沟通准备时间并控制承诺边界 |
| Skill 7 | 业务日报生成 | 当前客户结果与内存 Mock 今日客户 | 跨客户业务日报 | 验证客户排序、待办合并和风险汇总逻辑 |

## 4. Skill 1：客户信息解析

### 输入

客户备注、聊天记录、电话纪要、会议记录，以及业务员手动输入的其他客户信息。

### 处理目标

从非结构化文本中识别客户姓名或称谓、行业、角色、需求、关注点、预算、时间计划和当前阶段等业务信息，并保留必要的输入证据。

### 输出

结构化客户信息字段，以及关键字段对应的原文依据。建议输出字段包括：

- 客户姓名或称谓；
- 所属行业；
- 客户角色；
- 明确需求；
- 主要关注点；
- 预算信号；
- 时间计划；
- 当前阶段；
- 未知或待确认项；
- 原文证据片段。

### 关键规则

- 原文未出现的信息标注为“未知/待确认”；
- 根据上下文得出的非确定信息必须标注为“推断”；
- 不得将原文没有提供的信息写成事实；
- 关键字段必须尽量保留可回溯的证据片段。

### 合格标准

- 关键事实字段提取完整度不低于 80%；
- 不出现关键事实臆造；
- 关键字段能够回溯到输入文本。

## 5. Skill 2：客户档案生成

### 输入

Skill 1 输出的客户信息解析结果。

### 处理目标

将分散字段整理为格式统一、层次清晰、便于浏览和核查的客户档案。

### 输出

- 客户称谓；
- 行业；
- 角色；
- 核心需求；
- 已知兴趣；
- 主要关注点；
- 预算；
- 当前阶段；
- 时间计划；
- 待确认信息。

### 关键规则

- 保持字段名称与数据格式统一；
- 合并语义重复的信息，不重复堆叠；
- 持续保留“事实/推断/未知”标签；
- 不因档案字段存在而强行补齐缺失信息。

### 合格标准

- 规定档案字段覆盖率不低于 90%；
- 信息归类清晰；
- 不出现明显字段错位；
- 缺失信息得到明确标注。

## 6. Skill 3：客户需求分析

### 输入

客户档案、关键原始证据片段和客户关注点。

### 处理目标

分析客户的显性需求、潜在痛点、决策阶段、成交阻碍、关注因素和待确认问题，为机会判断提供有边界的分析依据。

### 输出

客户需求分析报告，至少包括：

- 显性需求；
- 潜在痛点；
- 决策阶段；
- 关键关注因素；
- 成交阻碍；
- 待确认问题；
- 结论依据。

### 关键规则

- 显性需求必须能够从原文找到依据；
- 潜在痛点必须标注为“推断”，并说明验证方向；
- 不得虚构预算、决策权限或采购时点；
- 证据不足时应输出待确认问题，而不是补写结论。

### 合格标准

- 至少识别一项主要需求；
- 至少提出一项待确认问题；
- 关键结论与输入证据一致；
- 不将潜在痛点表述为确定事实。

## 7. Skill 4：业务机会判断

### 输入

客户需求分析、预算信号、时间信号、意向强度和风险因素。

### 处理目标

判断客户当前业务机会等级，并清楚说明支持该判断的证据、不确定因素和成交阻碍。

### 输出

- 机会等级；
- 有利信号；
- 不确定因素；
- 成交阻碍；
- 判断依据。

建议机会等级为：**高 / 中高 / 中 / 低 / 暂不判断**。

### 关键规则

- 机会判断必须审慎，并与当前证据强度匹配；
- 不能因为客户表达兴趣就直接判定为高意向；
- 必须同时输出有利信号和不确定因素；
- 预算、权限和时点缺失时，应降低判断确定性或使用“暂不判断”。

### 合格标准

- 机会等级与证据一致；
- 风险提示清楚；
- 有利信号与不确定因素均有呈现；
- 不夸大成交可能性。

## 8. Skill 5：跟进建议生成

### 输入

客户档案、需求分析和业务机会判断。

### 处理目标

将客户分析结果转化为业务员可以理解并执行的下一步行动。

### 输出

- 建议跟进时间；
- 沟通目标；
- 准备材料；
- 行动步骤；
- 优先级；
- 预期目标。

### 关键规则

- 每条建议必须包含动作、对象、时点和目标；
- 建议应符合客户当前阶段；
- 不跳过需求确认直接推进成交；
- 不能用笼统表述代替具体行动。

### 合格标准

- 至少 80% 的建议经评测者判断可执行；
- 建议与客户当前阶段一致；
- 不出现明显不合时宜的动作；
- 关键建议能够对应到需求、风险或待确认项。

## 9. Skill 6：沟通话术生成

### 输入

客户称谓、沟通渠道、客户关注点、跟进目标和禁止承诺项。

### 处理目标

生成可编辑、可直接参考的微信话术、电话话术或邀约话术，帮助业务员快速准备下一次沟通。

### 输出

一段自然、简洁、体现客户关注点且具有明确下一步的话术。

### 关键规则

- 不虚构客户或产品事实；
- 不承诺未经验证的价格、效果或交付条件；
- 不在需求尚未确认时直接强推成交；
- 语言应自然、克制，适合真实业务沟通；
- 最终发送前必须由业务员人工确认。

### 合格标准

- 无虚假承诺或虚构事实；
- 能体现客户至少一个核心关注点；
- 包含明确、合理的下一步；
- 经轻微编辑或无需编辑即可使用。

## 10. Skill 7：业务日报生成

### 输入

- 当前新客户经前序 Skills 生成的结构化结果；
- 后端内存中预置的 2—3 个“今日已处理”Mock 客户数据。

### 处理目标

将当前客户与 Mock 客户联合分析，验证跨客户汇总、优先级排序、待办合并和全局风险提醒等日报核心逻辑。

### 输出

- 今日新增或更新客户；
- 高优先级客户排序；
- 跨客户待办；
- 全局风险提醒；
- 明日计划；
- 数据范围说明。

### 关键规则

- Mock 客户只用于 W2 演示；
- Mock 数据不写入数据库；
- Mock 数据不代表真实历史数据；
- W2 不进行跨会话持久化；
- 页面刷新或服务重启后，演示数据恢复初始状态；
- Mock 汇总不等同于真实多客户管理；
- 真实多客户管理、历史记录和 Agent 记忆放到 W3 实现。

### 合格标准

- 覆盖当前客户和全部有效 Mock 客户；
- 高优先级排序有明确依据；
- 待办事项能够对应到具体客户；
- 风险提醒可以回溯到客户信息；
- 不将集合外客户或无依据动作写入日报。

## 11. 工作流中的事实边界控制

事实边界控制贯穿所有 Skills，而不是仅在最终输出阶段进行修正。W2 工作流采用以下规则减少模型幻觉：

1. **标注信息属性：** 对输入和判断结果标注“事实/推断/未知”。
2. **保留原文依据：** 对姓名、预算、时点、角色和关键需求等字段保留必要证据片段。
3. **不补写缺失信息：** 缺失内容统一标记为“未知/待确认”，并转化为后续沟通问题。
4. **约束沟通承诺：** 话术不得虚构价格、效果、案例或交付能力，不得承诺未经验证的结果。
5. **双面机会判断：** 机会判断必须同时列出有利信号和不确定因素，避免只呈现支持成交的单向证据。
6. **人工最终确认：** 输出仅作为业务员的分析与沟通参考，最终发送、报价和业务决策由人工确认。

建议的结构化字段示意如下：

```json
{
  "field": "budget",
  "value": null,
  "status": "unknown",
  "evidence": "客户尚未明确预算",
  "needs_confirmation": true
}
```

该示意用于说明数据边界，不代表 W2 必须建设数据库或完整数据平台。

## 12. W2 Demo 中的实现方式

W2 阶段采用网页 Demo 展示链式业务处理流程。目标交互如下：

1. 用户在网页输入一段客户信息或沟通记录；
2. 用户点击“一键生成业务处理报告”；
3. 系统按顺序执行信息解析、档案生成、需求分析、机会判断、跟进建议和话术生成；
4. 系统将当前客户结构化结果与后端内存中预置的 2—3 个 Mock 今日客户联合汇总；
5. 页面输出客户档案、需求分析、机会判断、跟进建议、沟通话术和业务日报。

W2 实现边界如下：

- 使用内存 Mock 数据验证日报聚合逻辑；
- 不使用数据库，不提供跨会话持久化；
- 不接入真实 CRM；
- 不自动读取微信；
- 不接入日历或名片 OCR；
- 不提供登录注册、多用户权限或付费系统。

本文描述的是 W2 Demo 的目标工作流与验收口径。各环节是否已完成，应以实际代码、可运行页面和评测记录为准。

## 13. 与评测标准的对应关系

| Skill | 对应评测指标 |
|---|---|
| Skill 1：客户信息解析 | 信息提取完整度；需求分析准确性的证据基础 |
| Skill 2：客户档案生成 | 客户档案结构化程度 |
| Skill 3：客户需求分析 | 需求分析准确性 |
| Skill 4：业务机会判断 | 业务机会判断合理性 |
| Skill 5：跟进建议生成 | 跟进建议可执行性 |
| Skill 6：沟通话术生成 | 沟通话术可用性 |
| Skill 7：业务日报生成 | 业务日报完整度 |
| 整体网页工作流 | 用户操作简易度；端到端输出一致性 |

每个 Skill 可使用固定测试输入独立评测，再通过端到端案例检查跨 Skill 的字段传递和结果一致性。详细评分权重、评分方法和合格标准以 [`docs/05_evaluation.md`](05_evaluation.md) 为准；示例评测结果应在 Demo 完成后依据实际运行结果填写，不预先将目标值表述为已达成结果。

## 14. 总结

知客 ZhiKe AI 的 Skills / Workflow 设计目标，是把业务员依靠经验完成的客户理解、需求判断、跟进准备和日报汇总过程，拆解成可运行、可评测、可迭代的 AI 工作流。W2 阶段重点验证网页 Demo 的核心业务闭环、事实边界和评测标准，不扩展为完整 CRM；后续 W3/W4 再逐步验证真实多客户管理、历史记录、Agent 记忆、外部系统接入和企业级能力。
