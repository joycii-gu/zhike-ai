# 知客 ZhiKe AI：Prototype 使用说明

> 项目副标题：面向业务员的 AI 业务处理智能体  
> 适用阶段：S3 全球青年培育赛 · W2 复赛 · X创新赛道  
> 文档定位：W2 网页 Demo 运行、使用与验证说明

## 1. 文档目的

本文件介绍知客 ZhiKe AI 在 W2 阶段的网页 Demo 使用方式、本地运行方式、功能范围和验证目标，帮助评委快速了解并测试 Prototype。

W2 阶段的目标是跑通可运行原型，而不是建设完整商业系统。Demo 用于验证“客户信息输入 → 客户档案生成 → 客户需求分析 → 业务机会判断 → 跟进建议 → 沟通话术 → 业务日报”的核心业务闭环。评委可通过一次输入和一次生成操作，观察从原始客户信息到结构化业务结果的完整处理过程。

本文定义 W2 Demo 的目标交互和验收口径。具体功能是否已完成，应以仓库中的实际代码、可运行页面和评测记录为准，不能仅由本文档替代证明。

## 2. Prototype 概述

知客 ZhiKe AI 的 W2 Prototype 是一个网页 Demo，建议使用 Streamlit 实现，以低开发成本完成交互展示和核心工作流验证。

Prototype 的目标使用流程如下：

1. 用户输入一段客户信息或沟通记录；
2. 点击“一键生成业务处理报告”；
3. 系统依次输出客户档案、客户需求分析、业务机会判断、跟进建议和沟通话术；
4. 系统将当前客户结果与后端内存中预置的 2—3 个 Mock 今日客户联合汇总；
5. 系统输出包含客户排序、跨客户待办和风险提醒的业务日报。

Mock 客户只用于 W2 演示，不代表真实数据库、真实客户数据或历史记录。W2 Prototype 不提供真实多客户管理和跨会话持久化。

## 3. 本地运行方式

当 `zhike-ai/app.py` 与 `zhike-ai/requirements.txt` 已齐备时，在项目所在终端运行：

```bash
cd zhike-ai
pip install -r requirements.txt
streamlit run app.py
```

运行说明：

- 首次运行前，使用 `pip install -r requirements.txt` 安装依赖；
- 使用 `streamlit run app.py` 启动网页 Demo；
- Streamlit 会在终端显示本地访问地址，通常为 `http://localhost:8501`；
- 在浏览器中打开终端显示的地址即可体验 Demo；
- 如果默认端口被占用，应使用 Streamlit 实际提示的其他端口；
- 如项目需要模型 API，应先按照项目配置说明设置必要的环境变量，不应将密钥直接写入代码或提交到仓库。

以上命令是 W2 Demo 的目标运行方式。若对应代码或依赖文件尚未提交，则需先完成文件准备，不能仅凭运行说明认定 Prototype 已可运行。

## 4. 页面功能说明

### 4.1 项目介绍区

页面顶部展示项目名称、项目副标题、一句话说明和核心业务闭环，使评委无需阅读长文即可理解 Demo 的用途。

建议展示：

> 知客 ZhiKe AI：面向业务员的 AI 业务处理智能体  
> 客户信息输入 → 客户档案生成 → 客户需求分析 → 业务机会判断 → 跟进建议 → 沟通话术 → 业务日报

### 4.2 客户信息输入区

用户可粘贴客户备注、聊天记录摘要、电话纪要、会议记录或业务员手工记录。输入区不要求用户预先整理成固定表格，但应提醒用户避免输入不必要的敏感个人信息。

### 4.3 示例案例选择区

Demo 建议至少提供以下 3 个示例案例，方便评委快速测试：

- 企业培训客户案例；
- 课程顾问客户案例；
- 企业服务客户案例。

选择示例后，可将案例内容填入输入区，用户仍可继续编辑。

### 4.4 一键生成按钮

按钮建议命名为：

> **一键生成业务处理报告**

点击后启动链式 Skills 工作流。处理期间建议显示明确的运行状态，并防止用户重复提交。

### 4.5 输出结果区

输出结果建议按以下顺序展示：

1. 客户档案；
2. 客户需求分析；
3. 业务机会判断；
4. 跟进建议；
5. 沟通话术；
6. 业务日报。

各模块应使用固定标题和结构，便于评委对照输入、检查事实边界并执行评测。

### 4.6 数据范围说明区

页面应明确提示：业务日报使用“当前输入客户 + 后端内存 Mock 今日客户”生成；Mock 数据不写入数据库，不代表真实历史记录，也不构成真实多客户管理。

## 5. 输入格式说明

### 5.1 原始记录优先

业务员不需要先把客户资料整理成表格或总结稿。可以直接粘贴原始微信聊天记录、电话纪要、会议记录或零散备注，知客会先完成信息解析，再生成后续业务结果。

页面提供输入类型选择，并支持补充客户称谓、沟通渠道和计划跟进时间。这些补充字段均为可选，不影响直接使用原始记录生成报告。

如果预算、决策人或采购时间等信息没有出现在原始记录中，系统应输出“未知/待确认”，不要求业务员预先补齐，也不允许模型自行臆造。

用户可以直接输入自然语言，不需要遵循严格表格或 JSON 格式。系统可接受的输入类型包括：

- 客户咨询记录；
- 微信聊天摘要；
- 电话沟通纪要；
- 会议记录；
- 业务员手动备注；
- 名片信息的文字描述。

“名片信息的文字描述”仅指用户手动输入或粘贴的文本。W2 Demo 不包含名片 OCR，也不会自动读取图片。

### 示例输入

> 李总，做企业培训，最近想了解 AI 员工如何帮助销售团队做客户跟进。之前看过我们的 HermesAgent 安装服务，对 AI 业务助理感兴趣，但还没有明确预算，希望下周约一次线上沟通。他比较关心部署难度、价格、实际效果，以及业务员是否真的会用。

输入中未提供的信息应在输出中标注为“未知/待确认”，不能由模型自行补写为事实。

## 6. 输出模块说明

### 6.1 客户档案

客户档案用于将零散记录整理为统一客户视图。建议输出客户称谓、行业、角色、核心需求、已知兴趣、主要关注点、预算、当前阶段、时间计划和待确认信息。

关键字段应区分事实、推断和未知；例如，输入未明确客户角色时，应标注“未知/待确认”或“推断”，而不是直接认定其为决策人。

### 6.2 客户需求分析

客户需求分析用于识别显性需求、潜在痛点、决策阶段、成交阻碍、关注因素和待确认问题。显性需求必须来自输入证据，潜在痛点必须标注为推断。

### 6.3 业务机会判断

业务机会判断输出机会等级、有利信号、不确定因素、成交阻碍、判断依据和风险提醒。判断应保持审慎，不能因为客户表达兴趣就直接判定为高意向。

### 6.4 跟进建议

跟进建议将分析结果转化为业务员可以执行的行动，包括建议跟进时间、沟通目标、准备材料、行动步骤、优先级和预期目标。每项关键建议应尽量具备动作、对象、时点和目标。

### 6.5 沟通话术

系统生成一段可编辑、可直接参考的微信、电话或邀约话术。话术应体现客户关注点，包含合理的下一步，不虚构事实，也不承诺未经验证的价格、效果或交付条件。最终发送前应由业务员人工确认。

### 6.6 业务日报

业务日报联合当前客户和 Mock 今日客户，输出：

- 今日新增或更新客户；
- 高优先级客户排序；
- 跨客户待办；
- 全局风险提醒；
- 明日计划；
- 数据范围说明。

该模块用于验证跨客户汇总逻辑，而不是模拟真实数据库或长期客户管理系统。

## 7. Mock 客户机制说明

W2 Demo 后端内存预置 2—3 个被标记为“今日已处理”的 Mock 客户。当用户提交当前客户后，系统会将当前客户的结构化结果与 Mock 客户联合分析，生成跨客户业务日报。

Mock 机制用于验证以下能力：

- 跨客户信息汇总；
- 高优先级客户排序；
- 待办事项合并；
- 全局风险提醒；
- 明日行动计划生成。

Mock 数据的边界如下：

- 仅用于 W2 演示；
- 不写入数据库；
- 不进行跨会话持久化；
- 页面刷新或服务重启后恢复初始状态；
- 不代表真实客户数据或真实历史记录；
- 不等同于真实多客户管理。

真实多客户管理、历史跟进记录和 Agent 记忆计划在 W3 阶段实现。

## 8. Demo 验证目标

W2 Prototype 主要验证以下问题：

1. 用户能否以较低操作成本输入客户信息；
2. 系统能否生成结构化客户档案；
3. 系统能否区分事实、推断和未知；
4. 系统能否完成有证据边界的客户需求分析；
5. 系统能否给出审慎的业务机会判断；
6. 系统能否生成可执行的跟进建议；
7. 系统能否生成可供人工确认的话术；
8. 系统能否通过 Mock 数据演示跨客户业务日报；
9. 整个流程是否适合业务员快速使用。

上述内容是验证目标，不应在完成实际测试前直接表述为已达到的效果。验证结论应由测试案例、实际输出和评分记录支持。

## 10. 与评测标准的对应关系

Demo 通过固定输入、结构化输出和可重复操作支持评测。建议评测者使用相同案例独立评分，并保留输入、输出、模型版本、评分和问题记录。

| 评测指标 | Demo 中如何观察 |
|---|---|
| 信息提取完整度 | 将档案中的关键事实与原始输入逐项比对，检查遗漏和臆造 |
| 客户档案结构化程度 | 检查字段覆盖、归类、缺失标注和可读性 |
| 需求分析准确性 | 检查显性需求是否有证据、潜在痛点是否标注推断 |
| 业务机会判断合理性 | 检查机会等级、依据、不确定因素和风险是否一致 |
| 跟进建议可执行性 | 检查建议是否具备动作、对象、时点和目标，并符合客户阶段 |
| 沟通话术可用性 | 检查话术是否自然、针对、有下一步且无虚假承诺 |
| 业务日报完整度 | 检查当前客户与 Mock 客户是否均被纳入，排序、待办和风险是否可回溯 |
| 用户操作简易度 | 记录完成核心流程所需操作步骤、任务完成率和测试者反馈 |

详细评分方法和合格标准应记录在 [`docs/05_evaluation.md`](05_evaluation.md)；示例评测结果应基于实际 Demo 运行结果填写，不预先将目标值表述为已达成结果。

## 11. W2 范围边界

当前 W2 Demo 不包含：

- 登录注册；
- 数据库；
- 跨会话持久化；
- 真实 CRM 接入；
- 微信自动读取；
- 名片 OCR；
- 日历自动同步；
- 多用户权限；
- 付费系统。

真实多客户管理、历史记录和 Agent 记忆属于 W3 规划；微信、CRM、日历、名片 OCR 等外部系统接入属于 W4 规划。这些能力不能在 W2 中作为已实现功能宣传。

## 12. 常见问题

### 1）这个 Demo 是完整 CRM 吗？

不是。W2 只验证从客户信息输入到业务报告和跨客户日报输出的核心业务处理闭环，不提供完整 CRM 的数据管理、权限、集成和运营能力。

### 2）Mock 客户是真实客户数据吗？

不是。Mock 客户是后端内存中预置的演示数据，不代表真实客户或历史记录，也不写入数据库。

### 3）业务日报为什么会出现多个客户？

为了验证跨客户汇总能力，系统会将当前输入客户与 2—3 个 Mock 今日客户联合分析，演示排序、待办合并和全局风险提醒。

### 4）输出内容可以直接发给客户吗？

沟通话术可以作为编辑参考，但模型输出可能存在遗漏或误判，最终发送前应由业务员核对事实、调整表达并人工确认。

### 5）后续会接入微信、CRM 或日历吗？

这些属于 W4 规划。W2 不包含真实外部系统接入，后续是否实施还需经过接口、权限、合规和安全验证。

## 13. 总结

知客 ZhiKe AI 的 W2 Prototype 通过网页 Demo 验证从客户信息输入到业务行动生成的核心流程，重点展示结构化业务工作流、事实边界控制、可执行建议生成和跨客户日报机制。W2 的结论应以可运行页面和实际评测结果为依据，并为 W3 的真实多客户管理、历史记录与 Agent 记忆，以及 W4 的外部系统接入打下基础。
